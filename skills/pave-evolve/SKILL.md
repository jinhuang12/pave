# PAVE Evolve

Revise one delivered PAVE workflow from evidence. You are the lead of one revision: you verify the base, brief the two seats, present the approval gate where the contract requires one, and apply. You never draft the successor and never judge it — a lead that redesigns its own graph from a run-filled context is the actor this skill replaces (`references/pave-revisions.md`, One drafting path).

This skill is manual-only. Do not start it from an implicit match. Every `references/...` and `scripts/...` path below resolves under the pave-init skill directory of this plugin; the update path itself is declared in `references/pave-init.pave.yaml` (`draft_successor`, `review_successor`, `approve_successor`, `apply_revision`).

## Inputs

The requester — a PAVE lead paused on a defect in its own graph, or the user — supplies by path:

- the revision folder: the live `workflow.pave.yaml` (with any children), `revisions.yaml`, `history/`;
- the defect evidence: run-state entries, the standing review record section, or the user's own description — for pave-init itself, the release's review record;
- the usage records the predecessor runs left (`references/pave-revisions.md`, revision rule 8), or the statement that none exist;
- the plan's revision-record fields `approval` and `usage_log` from `skill-package-plan.md` — for pave-init itself, `approval: always`.

Run `scripts/record_revision.py verify <root>` before anything else — for pave-init itself, the substitute named under `references/pave-revisions.md`, pave-init itself. A failure is the first defect to route: an unrecorded edit is blocked honestly and handed to the seats as evidence, and an interrupted apply step (`.applying` present) is restored from version control and its marker removed before `verify` passes — a proposal against an unverified base applies on the wrong digest.

## Procedure

1. **Draft** (`draft_successor`). Brief the workflow-updater with the inputs above and the revision number it may propose (head + 1). Batch by pause or by audit checkpoint: one proposal covers every defect recorded since the last apply step. Route its outcome:
   - `draft_ready`: go to step 2.
   - `needs_user_approval`: go to `pause_for_user_authority` with the user-only change the updater reported. The draft records `user_only_changes: pending`; `propose` accepts that value and `apply` refuses it. The user decides before more work is spent. If the user proceeds, re-enter this step with the response recorded verbatim; the draft then carries `user_only_changes: approved` and still passes steps 2 and 3. If the user declines, close at `closed_no_change`.
   - `no_change_needed`: close at `closed_no_change` and record why in the requester's evidence. If the request is an audit checkpoint and the write report trend rose since the previous checkpoint, this close first needs step 2's PASS on the no-change. A checkpoint that cost more than the last one and proposes nothing is the claim most worth attacking.
2. **Review** (`review_successor`). Brief the update-reviewer with the proposal path, the root, and the defect evidence; it applies the patch to a scratch copy itself. `passed` → step 3 when approval is required, else step 4. `revision_required` → send the findings to the same updater and re-review with the same reviewer. After three rounds that still carry a verified `BLOCKING` or `HIGH` finding, pause for the user with the open findings — that is the graph's bound (`update_review_rounds_remain`), not a judgment call. The round count lives in the requester's run state when a paused run asked for the revision (`plan_review_rounds` for a pave-init run, the generated lead's own counter otherwise); a user-requested revision lives in one session and counts its rounds in the conversation.
3. **Approve** (`approve_successor`) — only when the preamble's user-only-changes check is `approved` or the plan says `approval: always`. Present the semantic diff, the declared `kind`, `digest_before → digest_after`, the cost per run, and the review verdict; the approval option names the revision number and the digest. `approved` → step 4 with the response verbatim. `revision_requested` → step 1 with the user's words. `rejected` → `closed_no_change`; remove the unapplied proposal file.
4. **Apply** (`apply_revision`). `scripts/record_revision.py apply <root> <N> --approval "<verbatim>" --review "<verdict and rounds>"` — add `--commit` when the root is tracked — then `verify`. To apply an audit checkpoint's proposal, add `--proposal <revision-folder>/proposals/<checkpoint>-<run-setup|graph>.patch --hook-records <run-state>.audit-checkpoint.json`. The entry then records `written_by: workflow-updater`. The stop guard closes the checkpoint only when that entry's patch bytes equal a proposal file the guard itself hook-recorded in the sidecar. Without the two flags the entry records `written_by: unverified`, and the checkpoint never closes. `applied` → hand back. `apply_failed` → pause for the user with the tool's output; never patch the live graph by hand to finish an apply step.

## For pave-init itself

pave-init has no revision folder. Its live graph is `references/pave-init.pave.yaml` in its source repository, and its apply step is a release: the proposal is a patch against the sources — never the generated lead skill or agent files, whose header says so — and the apply step is the build, the tests, the document size test, and a changelog entry carrying the semantic diff. Approval is the user's, always.

## Hand-back

Return to the requester: the revision number, `kind`, `digest_after`, the review verdict and round count, the approval or the record that no user-only change was touched, and the revision log path. The requester's lead re-pins its run to the new revision and continues from its last satisfied gate (revision rule 7). This skill never writes another workflow's run state.

## Multi-agent contract

Both seats are registered agent types from this plugin. A role contract is the harness-loaded system prompt, so a brief carries task context, not a role file to read. Resolve this plugin's absolute installation path before dispatch and include the pave-init skill directory (`<plugin-root>/skills/pave-init/`) in every brief so seats can resolve `references/...` and `scripts/...`.

- Start the updater with the Agent tool, `subagent_type: pave-init:workflow-updater`, a unique `name`, and `run_in_background: true`; continue that same updater through review rounds with `SendMessage` — a fresh updater re-derives the proposal and loses the rounds' record.
- Start the reviewer with `subagent_type: pave-init:update-reviewer`, a unique `name`, and `run_in_background: true`; continue that same reviewer through repair rounds with `SendMessage`.
- Use the model and effort in agent frontmatter.
- Use `AskUserQuestion` for the approval gate; the approval option names the revision number and digest. If the tool is unavailable, ask the same bounded question in plain text.

If `pave-init:workflow-updater` or `pave-init:update-reviewer` is unavailable, pause and report an incomplete pave-init installation. Do not substitute an ordinary worker and claim equivalent review.

Reviewer continuity is part of the gate's evidence. Never re-brief a fresh reviewer mid-gate and present it as the same reviewer. A tool-forced selection is not approval of anything its visible option label did not state; require an explicit response that names the revision and digest being approved.
