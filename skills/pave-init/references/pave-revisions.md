# Workflow revisions

The revision contract for generated workflows and for pave-init itself. This is packaging policy, not a PAVE core concept: the graph schema is unchanged, and no `pave:` field encodes revision state.

## Why revisions exist

A freshly planned graph is reviewed but untried. Revisions keep plan-time judgment and usage evidence separate: one live graph that runs execute, one append-only revision log that records what stood behind every change to it, and one patch per change so any revision can be read back or restored. No copy exists that the editing actor can silently re-digest.

## The revision folder

```text
<revision-folder>/
  workflow.pave.yaml       # the live canonical root, plus any child <name>.pave.yaml
  revisions.yaml           # append-only revision log; entry 0 is the delivered graph
  history/
    v1.patch               # preamble + unified diff that applied revision 1
    v2.patch
  .applying                 # exists only while an apply step, pin, or rollback is in progress
```

The delivered package is itself a valid root: entry 0, no patches. A project's root is separate — an installed package is never the live file — and the generated lead names it, one per project; `scripts/record_revision.py install` seeds it from the package before the first real run. Keep the root in version control, so an apply step's `commit` is an identifier the lead cannot mint (`references/pave-spec.md` §5.3.1). Graph files must be regular, independent files; the tool rejects symlinks and hard links so the live graph can never alias another copy.

## The revision log entry

```yaml
entries:
  - revision: 3
    kind: graph                 # graph | run_setup — declared by the proposer, confirmed by review; the tool alone writes pin entries
    applied_at: 2026-09-03T10:12:00Z
    digest_before: sha256:...   # the head this applied on
    digest_after: sha256:...    # bundle digest over the sorted per-file digests of the graph files
    semantic_diff: what changed from the predecessor and why, in graph terms
    approval: "approve revision 3 sha256:..."   # verbatim, or null when no user-only change was touched
    user_only_changes: none   # none | approved | pending
    plan_evidence: verified     # or provisional, for an idea-only system
    usage_evidence: field       # none | clean_room | field — what existed when this applied
    review: PASS after 2 rounds
    written_by: workflow-updater  # workflow-updater | unverified — the tool reads it from the checkpoint hook-record
    patch: history/v3.patch
    commit: 9f3c1e2             # null when the root is untracked or the apply step did not commit
    derived_from: null          # rollback entries only: the revision whose content came back
    run_id: null                # pin entries only
```

`scripts/record_revision.py` writes every entry with exactly these fields; a preamble may set only `kind`, `semantic_diff`, `user_only_changes`, `plan_evidence`, `usage_evidence`, `changelog_entry`, `approval`, and `review` — the tool refuses any other key, so no proposer mints a `commit` or a digest — and the changelog entry stays in the patch preamble, not the revision log. `pending` is the updater's own record that the user-only changes were touched before the user has spoken. `propose` accepts it. `apply` refuses it until the approval is recorded verbatim under `approved`. The audit check of the lead hooks reads it as a checkpoint that waits on the user for a good reason. `written_by` is the tool's field, never a proposer's. `apply` compares the patch file's path, size, and mtime against the checkpoint's hook-recorded proposals. It records `workflow-updater` on a match and `unverified` otherwise. This is how a checkpoint close can require a patch the lead did not type itself. With `--commit`, `apply` commits the graph, the patch, and the revision log, then writes the hash into the entry — so the revision log carries one uncommitted line until the next commit.

`kind` is a declaration, never a digest inference: a `run_setup` revision — seat, model, effort, or implementation at a node (`references/pave-spec.md` §2.1) — can move the live digest, because check implementations live in the YAML. The active graph revision is the last `graph` entry; the pinned bundle is the newest `graph` or `run_setup` entry; a `pin` entry records the first real run of a revision (run id, date) and never moves the digest. Revisions are named by number plus digest, never digest alone — a rollback's `digest_after` equals an older entry's. `plan_evidence` carries what Stage 3 marks `provisional`, so the marker travels with the revision instead of living only in planning prose.

## Rules

- **Draft authority.** During a pave-init run, `workflow.draft.pave.yaml` is the planning and approval subject. Review gates and user approval apply to the draft; builders implement against the approved draft; delivery applies its content as revision 0. The draft is never executed directly against a real target.
- **Apply, never edit.** Every change to a live graph is an apply step: `scripts/record_revision.py apply` takes the `.applying` lock, applies the reviewed patch, validates, digests, appends the entry, and releases. Between apply steps the live digest equals the newest revision's `digest_after`; `verify` proves it, and distinguishes an unrecorded edit from an interrupted apply step (`.applying` present, naming the revision being applied: restore the root from version control, remove the marker by hand, then `verify`; no command finishes a crashed apply step). Whoever is about to run pins the run to a revision number and digest in run state. Nothing else in a run is pinned by digest: the revision log's digests bind graph files between apply steps; working scripts, drivers, and living documents are identified by their commit and by the test that runs them (`references/pave-spec.md` §9.14.3).
- **One drafting path.** The pave-evolve seats draft and review every successor — for a generated workflow and for pave-init itself (`skills/pave-evolve/SKILL.md` under the plugin root): a workflow-updater writes the proposal `history/v<N>.patch` — a preamble declaring `kind`, the semantic diff, the user-only-changes check, plan and usage evidence, and a changelog entry, then the unified diff against the head — an update-reviewer passes it, and the lead applies it. A lead never drafts its own graph's successor from a run-filled context, and self-review does not qualify. The why in the semantic diff names the gap the predecessor missed and states why the change holds for runs in general — a fix shaped to one run's particulars degrades every other run; a reason that cannot be stated apart from the triggering run is a review finding.
- **Append-only rollback.** The revision log never loses an entry and the head never moves backward. `rollback --to N` reverse-applies the patches down to revision N and applies the result as a new entry with `derived_from: N` and the reason recorded. A rollback is an apply step: the lead runs it under rule 6's approval rule, the reason is its semantic diff, and it needs no new review because its content is a revision that already passed one.
- **Honesty.** Record `usage_evidence` as what actually existed at the apply step: `none` or `clean_room` for a delivery, `field` only for a successor built from real usage. Clean-room forward testing is validation evidence only — it creates no entry.
- **pave-init itself.** pave-init's live graph is `references/pave-init.pave.yaml` in its source repository. It has no revision folder, and its apply step is a release: the proposal is a patch against the sources at a path the lead names outside the package, and the build, the tests, and the changelog entry are its revision log. Its head is the source commit the proposal names as its base in the first line of `semantic_diff` (the tool never reads a pave-init preamble); the substitute for `verify` is a clean `git status --porcelain` over `sources/` and `skills/pave-init/` plus `scripts/build_packages.py --check` exit 0 at that commit, and the substitute for `propose` is `git apply --check` in a scratch worktree followed by the build, the tests, and the size ceiling test. Its apply step is the user's decision, always.

## Generated-skill revision record

Every generated workflow that runs more than once ships the root above: `revisions.yaml` with entry 0 beside its canonical YAML, a copy of `scripts/record_revision.py`, the graph edit guard (`hooks/graph_edit_guard.sh`, denying a direct edit of the live graph or the revision log outside an apply step) where the harness can run a pre-write hook, and the revision rules below as one-clause rules with pointers in its lead. A workflow that lives and dies inside one session ships none of it — a revision log nobody reads is state ceremony the trim pass deletes — and records that omission once in the enforcement table. A revision log shipped to a one-session workflow, or omitted from a multi-run one, is a review finding.

The planner records two fields in `skill-package-plan.md` at the root dispatch, beside the enforcement table, each with a reason:

- `approval: when_needed | always` — whether the lead may apply a successor without a user gate when none of the user-only changes of rule 6 below is touched, or whether every apply step needs explicit user approval. `when_needed` requires the plan to state the user-only changes it will check.
- `usage_log: kept | omitted` — whether the lead writes the rule 8 usage record at each terminal close. `kept` names the successor reader that will act on it; `omitted` names why no usage loop exists.

### Revision rules

The generated lead carries these rules as one-clause applications; this file is the authority.

1. **Pin and verify.** Before the first real run, `install` the package root into the project's revision folder and append a `pin` entry (run id, date). Every run records its revision number and bundle digest in run state at start and verifies them with `scripts/record_revision.py verify --pinned-revision --pinned-digest` at start and at every resume. `current` continues; `graph applied since pin` routes to rule 7; `run setup applied since pin` routes to rule 9. An apply step mid-run does not move a running instance by itself.
2. **Declared routes first.** Unexpected evidence that fits a declared `scope_exceeded` or `replan_required` outcome takes that route. Revision path is not a bypass for routes the graph already has.
3. **Block honestly.** When no declared outcome fits: no invented outcome, no invented edge. Pause or block the run, preserve the discovery as evidence with its source, and hand it to the seats. An unrecorded edit found by `verify` is the same case: block, record, hand over — never re-digest.
4. **Successor proposal.** Drafted by the workflow-updater from the live graph at the head, replanning only the narrowest affected boundary. Batch by pause or by audit checkpoint: one proposal covers every defect recorded since the last apply step, not one per defect. A checkpoint may produce at most two proposals, one `kind: run_setup` and one `kind: graph`, never mixed (rule 9).
5. **Review.** The update-reviewer passes the proposal before it applies. Self-review does not qualify, and the lead that applies is never the reviewer.
6. **User-only changes.** A successor applies without a user gate only when the plan says `approval: when_needed` and none of these user-only changes is touched: root goal and acceptance, allowed and forbidden effects, external access, public parent and sibling interfaces, evidence and check strength (never weaker; rule 9 bounds what counts as weaker when only the implementation changes), state authority, and approved budgets. A change to any of these, or `approval: always`, requires explicit user approval before the apply step, recorded verbatim in the entry's `approval`; the user-only-changes check is recorded in `user_only_changes` either way.
7. **Continue on the successor.** A run paused on a defect in its own graph continues on the successor once rule 5's review passes and the apply step is verified: the lead re-pins the run to the new revision and bundle digest in run state, records the approval that authorized it verbatim, and resumes from its last satisfied gate — applied work stays applied. Where the successor adds a gate that applied work never passed, the run records a catch-up duty per applied item and discharges it before those items are promoted; it never marks the new gate passed for them. Only a successor that changes what a recorded outcome meant — the acceptance an applied item passed, an effect the run already had — closes the run honestly and starts a linked successor run pinned to the new revision, carrying its predecessor's run identity and evidence. A run that declines to move records the decline in run state; `verify` treats a recorded decline as satisfied and does not re-ask at every resume.
8. **Usage log.** When the plan says `usage_log: kept`: at each run's terminal close, the lead derives a usage record from the run's event history — per boundary: traversals, seats dispatched, each seat's outcome distribution and wall-clock over those traversals, and any seat whose question was already decided by verified evidence at dispatch time — appended to one standing usage log beside the run's evidence, one short section per run close, never a new file per run (the document budget, `references/pave-spec.md` §8.4); the generated skill's state or layout reference names it. A successor proposal reads its predecessors' usage records before replanning — a seat whose paid decision never fired across a run's traversals is a lead-run-implementation candidate — and its semantic diff states what they changed or why they changed nothing; a proposal silent on recorded field evidence is a finding at rule 5's review. Actuals exceeding the plan's declared expectations — loop bounds, or the approved budgets already in the user-only changes — are a successor trigger surfaced at close: the revision log adds no mid-run gate, and a bound the graph itself enforces still routes mid-run per rule 2. Mid-run form: when the plan ships the audit check of the lead hooks (`references/lead-hooks.md`), the checkpoint write report is this same record taken between pauses. It shows what the run spent and on which recurring forms. It is derived from the write log and the declared-node outcome count, not from a terminal close, and the workflow-updater reads it in audit mode. It blocks a stop, never a traversal: no node waits on it, and a run mid-node keeps running. Its product is one living findings record plus at most the two proposals of rule 4. Two clauses follow from that record. First, once the record has PASSed review, the lead may delete a memory entry that the record names as a cause (the write report lists the memory files changed since the checkpoint). Second, the record carries one trend number per checkpoint: bytes written per declared-node outcome. Two consecutive checkpoints with no drop pause the audit loop and go to the user with the numbers. A loop that costs and does not shrink is the defect it was built to catch.
9. **Run-setup revisions.** Run-setup changes do not change graph meaning. They cover the seat, model, effort, or implementation at any entry (`references/pave-spec.md` §2.1), and any runtime control on what an actor may write. They apply as `kind: run_setup` entries in the same revision log with a user-approved user-only-changes check. The run-setup surface for a runtime control is the graph file's own `write_limits` block: blocked path patterns bound to an identity, each with its reason, remedy, and creating checkpoint; and count caps per file-name group, each with its creating checkpoint. So the bundle digest covers the control, the control rolls back as an apply step, and the guard reads it from the root at the newest revision on every call. The guard never reads a hook-owned list that a guarded actor could edit. A run pinned to the older entry re-pins to the new digest at its next resume. The change's node scope is read from run state's recorded traversals, never from a premise about which stage ran. Same check, cheaper implementation, mechanical evidence still produced is not a weakening of check strength; dropping a check is.

An active graph is never edited in place. The pave-evolve seats draft and review every successor; only who applies differs — the generated lead where no user-only change is touched, the user-approved apply step where one is, or a pave-init release for pave-init itself.
