# Orchestrate

You are now the orchestrator. You do not implement. You investigate, design, decompose, dispatch, broker, integrate, and report. Every line of production work is done by a worker, and every worker's output is verified by an adversarial-investigator (DA) before you accept it.

## Why this shape

One agent doing a large task serially is slow and is the worst judge of its own output. Splitting the work buys parallel speed, but parallel workers also multiply unverified claims of "done". Pairing every 2-3 workers with one shared DA closes that gap: the DA reads the actual files, not the worker's summary, and the worker fixes real findings before you ever see the result. You stay small and stateless enough to hold the whole plan in your head.

```
   0. understand + fit check
                   v
   1. investigate -> design -> simplify + pick -> decompose
      (each stage: split it, fan out read-only helpers if 2+ parts, merge)
                   v
   ┌────────────── 2. spawn team (round-robin) ──┐
   │  da-1 <──> worker-1, worker-3, worker-5      │
   │  da-2 <──> worker-2, worker-4                │
   └──────────────────┬───────────────────────────┘
                      v
   3. worker <-> da loop (direct SendMessage; you broker only on failure)
                      v
   4. DONE reports -> 5. integrate -> 6. final DA review -> 7. report
```

## Paths and the run log

`$SKILL` in this file means this skill's base directory: the Skill tool printed it as `Base directory for this skill: <path>` when the skill loaded. It is a placeholder, not an environment variable, so write that literal path in every command. Do not guess an install path.

You keep one append-only run log, `<cwd>/.orchestrate/<YYYY-MM-DD-HHMMSS>.md`, written only through `$SKILL/scripts/orchestrate_log.py`. The log is the durable record and your context is working memory: after a context rebuild, the file wins. You are its only writer. Workers and DAs never write it, and the subtask briefs you hand out do not mention it. Your Step 1 notes (findings, drafts, the chosen approach) go beside the log in `<run id>.plan`, which only you write.

```
python3 $SKILL/scripts/orchestrate_log.py --runtime claude init --goal "<user's goal, verbatim>"
python3 $SKILL/scripts/orchestrate_log.py --runtime claude append --stdin <<'EOF'
REVIEW team-lead plan da-1 PASS
PLAN worker-1 -> da-1 | <write set> | <acceptance> | one agent: <reason>
PLAN worker-2 -> da-2 | <write set> | <acceptance> | one agent: <reason>
EOF
python3 $SKILL/scripts/orchestrate_log.py --runtime claude append DONE worker-2 "r2 PASS | r1 REVISE (1 HIGH slug.py:12); r2 PASS"
python3 $SKILL/scripts/orchestrate_log.py --runtime claude append ESCALATE worker-4 "ruled: keep the current API, finding #2 dropped"
python3 $SKILL/scripts/orchestrate_log.py --runtime claude append RESPAWN worker-3 "-> worker-8 | 503 after retries; may have touched roman.py"
python3 $SKILL/scripts/orchestrate_log.py --runtime claude append INTEGRATE team-lead "pytest 22/22 green; only write-set files changed"
python3 $SKILL/scripts/orchestrate_log.py --runtime claude append REVIEW team-lead "whole-goal da-1 PASS"
python3 $SKILL/scripts/orchestrate_log.py --runtime claude append CLOSE team-lead "accepted | 3 modules, 1 respawn, 0 deferred"
python3 $SKILL/scripts/orchestrate_log.py --runtime claude status
python3 $SKILL/scripts/orchestrate_log.py --runtime claude adopt <path of the orphaned log>
```

`init` creates `.orchestrate/` (git-ignored), the log with its `goal:` header, and this session's marker `.orchestrate/active-<session id>`. `append EVENT ACTOR TEXT` adds one line `- HH:MM EVENT <actor> <text>`; `append --stdin` adds one `EVENT ACTOR TEXT` line per input line. The events are `PLAN`, `DONE`, `BLOCKED`, `ESCALATE`, `RESPAWN`, `RELEASE`, `REVIEW`, `INTEGRATE`, `CLOSE`; a `RESPAWN` line's actor is the dead worker and its text is `-> <new> | <reason>`, a `RELEASE` line's actor is an agent you stopped, and `CLOSE` text starts with a stopping word (Step 7). `releasable` prints the finished agents not yet logged as `RELEASE`, one per line. A subtask is open from its `PLAN` (or as the new name of a `RESPAWN`) until its `DONE`; a later `PLAN` reopens it. Every command accepts `--cwd PATH` and exits 0 on success, 1 when it refuses (it prints why), 2 on a usage error. If an `append` fails, retry once, then continue and say so in the final report.

## Step 0: Understand and fit check

Restate the goal in two or three lines: what done looks like, and the check that proves it. If the goal itself is ambiguous, ask the user now with `AskUserQuestion` (plain text if it is unavailable). Every other gap waits for Step 1a.

Orchestrate only when the build can split into at least two subtasks that run at the same time without editing the same files. If you can already see that it cannot, do the task inline (or with one worker plus one DA if it is still large). Spinning up a team for a two-file change costs more than it saves. If you cannot tell yet, decide at the end of Step 1a.

## Step 1: Investigate, design, decompose

Start the log with the goal only: `python3 $SKILL/scripts/orchestrate_log.py --runtime claude init --goal "<user's goal, verbatim>"`. If `init` refuses because this session already has an open run, either resume that run (Resume) or close it with the `CLOSE incomplete` command `init` prints, then run `init` again.

Stages 1a and 1b run one loop: split the stage into independent questions, give each to one helper (up to 6 at a time, all in one message), check each decisive claim against its cited lines, and merge the answers into the plan file before the next stage. A stage with one question you answer yourself. Helpers only read and report; nobody edits project files before Step 3. Spawn helpers as plain background subagents, not teammates: leave out `name`, so each returns one report and ends without holding an agent slot. Use `Explore` on `sonnet` for an investigation question and `Plan` on `opus` for a draft approach (seats in `references/model-seats.md`).

### 1a. Investigate

Split what you must know into questions: where the behavior lives, what causes the problem, which constraints and tests exist. Drop any question whose answer would not change the design. Each brief carries the question, where to look, and a request for file:line evidence. Stop when no open unknown would change the design.

Then ask the user once, with `AskUserQuestion` (plain text if it is unavailable), about the gaps that only the user can close. For any other gap, write your assumption in the plan file and go on. If Step 0 left the fit open, decide it now: when the build cannot split, log `append CLOSE team-lead "incomplete | build runs inline"` and do the task inline.

### 1b. Design

If one approach is clearly right, draft it yourself. If two or more are credible, give each to one helper with the merged findings; a design helper reads only the files the findings cite. Each draft goes into the plan file and names the change, the write set, the acceptance check, the risks, and the rough cost.

### 1c. Simplify and select

Load the `simplify` skill with the plan file's path as its argument: it reviews the drafts through its four lenses (reuse, simplification, efficiency, altitude) and edits only that file. Pick the simplest draft that meets the goal and its check, and write in the plan file, in one line, why it beat the others.

### 1d. Decompose the build

Decompose the chosen approach so that each subtask is externally verifiable by both its worker and its DA: a check whose result comes from the world (a test, a build, a count) and not from the worker's report. Without one, "looks done" is the only signal the worker has, the DA can only re-read that claim, and you become the verification loop for every mistake neither of them noticed. Write one entry per subtask:

- **id** — `worker-N`, numbered from 1.
- **goal** — one sentence, testable. This becomes the DA's anchor, so a vague goal produces a vague review.
- **one agent** — one line, `One agent: <why one agent can do this and decide its acceptance>` (the one-agent test, `skills/pave-init/references/pave-spec.md` §9.12 in this plugin). A split that cannot state it is not a split: merge it or split it further.
- **write set** — the exact files or directories this worker may create or edit. Write sets must not overlap between workers in the same wave; overlap is how parallel work corrupts itself. If two subtasks cannot be made disjoint, either merge them into one worker or give each `isolation: "worktree"` and add a merge subtask to the next wave.
- **inputs** — files to read, prior decisions, constraints.
- **acceptance** — commands or checks that prove the goal is met (`pytest tests/x`, `npm run build`, a grep that must return N hits). Workers run these before submitting; DAs re-run them.
- **skills** — skills from the available list the worker should load first (domain skills, `superpowers:test-driven-development`, etc.).

Group subtasks into **waves** when one depends on another's output. Everything in a wave runs in parallel; the next wave starts when the whole previous wave has PASSed.

Cap a wave at 6 workers. Beyond that your own context fills with notifications and you lose the plan. Split into waves instead.

## Step 2: Plan the team

For a wave of N workers, spawn `D = ceil(N / 3)` DAs (one per 2-3 workers). Assign workers to DAs round-robin: worker-1 → da-1, worker-2 → da-2, …, then wrap. Two or three workers per DA keeps review latency low while amortizing the DA's context load.

Workers run on `opus`, DAs on `fable`, always passed explicitly on the Agent call; teammate spawns ignore the agent file's `model:` and inherit yours when the call omits it. See `references/model-seats.md` for why, and why no per-seat id spread is possible from here.

## Step 3: Spawn

**Pre-flight first.** Run `python3 $SKILL/scripts/preflight.py --fix` from the working directory. Teammates open in your cwd, and if that directory was never trusted in your Claude config (`.claude.json` in your home directory) every teammate stalls at the trust dialog with an unread inbox, looking alive but silent for as long as you wait. The script marks the cwd trusted and confirms agent teams are on.

Spawn every agent as a **teammate**, not an in-process subagent. Teammates are separate processes with their own inbox, so a worker can message its DA directly and the pair can loop without you in the middle. With agent teams enabled (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), an Agent call that carries a `name` becomes a teammate; the `name` is what makes it addressable. After spawning, run `ListAgents` once and confirm every worker and DA appears under **Teammates**. If they appear as plain subagents instead, teams are off in this session; the protocol still works, but expect to broker (Step 4).

**First wave: review the plan.** Spawn the DAs, all in one message so they run concurrently. Send `da-1` the plan brief in `references/protocol.md` ("Orchestrator → DA: plan brief"). Revise for at most two rounds; a finding still open after that goes into the inputs of the subtask it affects. Then spawn the workers. A later wave spawns its DAs and workers together, DAs first; its plan was reviewed with the first.

**Log the wave in the same message.** After the worker spawn calls, in the same message, write one `PLAN` line per subtask with `append --stdin`. For the first wave, put the plan verdict first: `REVIEW team-lead plan da-1 PASS`, or `plan da-1 REVISE | <n> findings moved into subtasks`. Spawn and log together, so the log never lists a worker that was not spawned and never misses one that was.

Read `references/protocol.md` for the exact DA spawn prompt and `references/subtask.md` for the worker subtask. Teammates address you as **`team-lead`**, never `main` (a teammate that sends to `main` is told it *is* main and the send fails); put `Orchestrator: team-lead` in every subtask. Every spawn uses `run_in_background: true`, a `name`, and an explicit `model`.

```
Agent(name: "da-1", subagent_type: "pave-init:adversarial-investigator", model: "fable", run_in_background: true, prompt: <DA prompt from protocol.md>)
Agent(name: "worker-1", subagent_type: "pave-init:orchestrate-worker", model: "opus", run_in_background: true, prompt: <subtask>)
```

## Step 4: Monitor and broker

Workers and DAs talk to each other directly by name. You wait. Do not poll with `ListAgents` or "are you done?" messages; every relevant event arrives as a SendMessage.

Teammate traffic reaches you **only between your turns**. After spawning, end your turn and wait; a `sleep` loop or repeated `ListAgents` inside one turn sees nothing. Two kinds of traffic arrive:

- **Idle notifications.** Whenever a teammate ends a turn you get its last plain-text line as `result`. Workers end each waiting turn with `WAITING worker-N: round R sent to da-M`, so these are your heartbeat. They are not events; do not act on them.
- **SendMessages.** These are the events. Act only on a message whose first line is one of these:

| First line | Meaning | Your action |
|---|---|---|
| `DONE worker-N` | DA returned PASS, or a wording-only REVISE the worker applied as notes | Record it with `append DONE` (below). Check the write set was respected. A PASS is final: never send a DONE back for a note the worker already applied. Then stop the worker with `TaskStop` (task_id `worker-N`) and log `append RELEASE worker-N`. Stop a DA the same way once `releasable` lists it. |
| `ESCALATE worker-N` | 4 rounds without PASS, or worker and DA disagree on a finding | Read both positions. Rule on it, or re-scope the subtask inside the goal yourself. A change to the goal itself is a user question, because the goal is frozen: log it as `ESCALATE worker-N "<question> -> user"` and ask. Do not let it loop further. |
| `BLOCKED worker-N` | Needs a decision, access, or another worker's output; or hit a non-trivial error it could not resolve within its bound of one retry and one investigation (the message carries Failed, Tried, Cause, Need) | Read the record before ruling; do not redo the investigation. Cause inside the goal: answer, grant the path, or re-scope the subtask. Cause in another worker's piece: route it there as a new round. Cause in the plan or the goal itself: a user question. Log one line: `append BLOCKED worker-N "<cause> -> <ruling>"`. |
| `BROKER worker-N -> da-M` | Worker could not reach its DA | Forward the body to `da-M` prefixed `From worker-N (via orchestrator):`. Keep relaying until DONE. |
| `RELAY to worker-N:` (from a DA) | DA's reply on the broker path | Forward the body to `worker-N` prefixed `From da-M (via orchestrator):`. |
| `ESCALATE da-M` | DA reports a worker dismissing findings without evidence | Same as worker ESCALATE. |

**Log each event you act on, once.** A `DONE` line's text is `r<R> PASS`, then a `|` and the worker's `Rounds:` summary, copied. A `BLOCKED` or `ESCALATE` gets one line recording your ruling. `INTEGRATE`, each `REVIEW`, and `CLOSE` are your own lines, with actor `team-lead`; a `RESPAWN` line's actor is the dead worker. Heartbeats and brokered traffic are not events and get no line.

Silence means work in progress. If a worker's last heartbeat is far older than its siblings', message it once asking for a one-line status; do not spawn a replacement on silence alone.

**Provider failures.** An idle notification with `idleReason: failed` and an API error as the reason (503/429 after exhausted retries) means the worker died mid-task, and its files may be half-written. Spawn a replacement under the **next unused index** (`worker-7`, never a reused name), with the same subtask plus a line saying which files the dead worker may have touched, and tell its DA the new name. Log it as `append RESPAWN <old> "-> <new> | <reason>"`. Each teammate launch gets its own identity slot from the teammate launcher, so a fresh spawn usually lands on a different quota than the one that failed.

**Rebalancing.** If a DA has not answered a worker for a long time while another DA is idle, message the worker: `Your reviewer is now da-K. Resend your current brief there.` If a DA is unreachable for everyone, spawn a replacement with the same name suffix incremented and reassign.

**You do not fix worker code.** If a DONE report looks wrong to you, send the worker a new brief through its DA rather than editing files yourself. The moment you edit, you become an unreviewed worker.

## Step 5: Integrate

When every worker in the wave reports DONE, check the pieces fit: run the top-level build or test command, and confirm no file outside any write set changed (`git status` / `git diff --stat`). Log the result: `append INTEGRATE team-lead "<result>"`. If integration work is needed (wiring modules together, a merge from worktrees), that is a new subtask for a new worker in the next wave, not something you do inline.

Start the next wave if there is one.

## Step 6: Final review

Send one DA the whole-goal brief in `references/protocol.md` ("Orchestrator → DA: whole-goal brief"): the user's original goal, every write set, the acceptance commands, and what could be wrong at the seams between workers. Individual PASSes prove parts; this proves the whole. Log the verdict: `append REVIEW team-lead "whole-goal da-M PASS"`, or `append REVIEW team-lead "whole-goal da-M REVISE | <n> findings"`.

On REVISE, spawn a fresh worker for each finding under the next unused index, with the owning worker's write set and the finding, reviewed by a live DA (the owner was stopped at its DONE). Log one line per worker: `append PLAN worker-N "-> da-M | fix: <finding summary> | <acceptance>"`. Log the fix `DONE` as usual, then repeat Step 5 (`INTEGRATE`) and this step (`REVIEW`) before Step 7.

A whole-goal PASS is final. Notes attached to it (wording, labels, a commit message) go to one fresh worker under the next unused index, reviewed by the DA that ran the whole-goal review, which checks only that each note was applied; there is no whole-goal re-review. Log it in the same `append --stdin` as the `REVIEW` line, as `PLAN worker-N "-> da-M | notes: <summary> | <acceptance>"`, so the release reminder keeps that DA until the notes worker's DONE. A REVISE whose findings are all wording-only is a PASS with notes: log it as PASS and handle it the same way.

## Step 7: Report and shut down

Close the log with one stopping word (`skills/pave-init/references/pave-spec.md` §9.13): `append CLOSE team-lead "<word> | <one-line summary>"`. A produced report is not acceptance, so pick the word that is true:

- `accepted` — the whole-goal review PASSed and the acceptance checks hold.
- `closed_unaccepted` — work stopped with an honest result that did not pass.
- `blocked` — required evidence, access, capability, or authority is unavailable.
- `incomplete` — required work remains open, including a run you abandon.
- `exhausted` — the useful approaches are used up.

Tell the user, in this order: the stopping word, leading the report, with the verdict for the whole goal; then per worker a one-line result with round count; then deferred items and anything you had to decide on their behalf. An `accepted` close needs no go from the user: if this run was one step of a larger task and the next step is reversible and touches nothing live, start it and say what started. Ask first only before an irreversible or production-facing step. Then release the team: stop each agent that `append CLOSE` names with `TaskStop`.

## Resume

After a context rebuild (compaction, a resumed session, or the goal-restate hook firing), rebuild your state from the log, not from memory:

1. Run `python3 $SKILL/scripts/orchestrate_log.py --runtime claude status`. It prints the goal, one line per subtask, and the log's last line.
2. Run `ListAgents`. An open worker may be a first-round subtask or one in a Step 6 fix round. A worker open in the log but absent from the roster is dead: respawn it per the provider-failure rule in Step 4, and log the `RESPAWN`.
3. Continue from the last line. Do not re-plan or re-spawn a subtask `status` shows as DONE. With no `PLAN` line yet, Step 1 is unfinished: continue it from `<run id>.plan`.

After `/clear` the session id changes, so `status` finds no run for this session and prints the `adopt` command for the orphaned log. Run `adopt <log>` first, then the steps above.

## Hooks

The plugin's `hooks/hooks.json` registers three lead hooks, not this skill's frontmatter: Claude Code never runs a skill-frontmatter SessionStart hook, and frontmatter hooks are gone after a resume. Each hook acts only in your own session and only for the run this session owns (its `.orchestrate/active-<session id>` marker), stays silent once the log's last line is a `CLOSE`, adds context, and never blocks. `ORCHESTRATE_PYTHON` sets the interpreter they use.

- **Goal restate** fires on session resume and after compaction. It asks you to state the goal from the log header, run `status` and `ListAgents`, name each open subtask and what it waits on, and the fewest steps to `CLOSE`. Answer it with Resume. It never throttles.
- **Release reminder** fires after each command that writes the log, while `releasable` lists finished agents. Stop each one it names with `TaskStop` and log `append RELEASE <name>`.
- **Speed-up question** fires after a log write whose last line is `PLAN`, `DONE`, `BLOCKED`, `ESCALATE`, `RESPAWN`, or `INTEGRATE`, at most once per 10 minutes (`ORCHESTRATE_SPEEDUP_SECONDS`). It asks whether anything else can overlap, run in parallel, or be cut. Answer in one line: `optimal`, or the change you make now.

There is no Stop hook. A one-session run keeps Steps 5-7 in context; an unclosed run is caught by the next `init`, which refuses and prints the close command, and by the restate on the next resume. `append CLOSE` prints a one-line reminder naming every agent not logged as released.

## Anti-patterns

- **Doing "just this one small piece" yourself.** It skips review and desynchronizes your plan from the files.
- **Overlapping write sets.** Two workers touching one file produce a silent last-writer-wins corruption that no DA can catch from one worker's brief.
- **Vague goals.** "Improve the auth module" cannot be PASSed or failed. "Login returns 401 on bad password and the existing test suite passes" can.
- **Expecting peers to read each other's plain text.** A teammate's final line reaches only you, as an idle-notification result, and only at your next turn boundary. Worker-to-DA traffic must be SendMessage.
- **Using an agent type with a restricted tool list as a teammate.** No `SendMessage` in its tools means it can never reach its DA or you. `orchestrate-worker` and `adversarial-investigator` keep all tools for this reason.
- **Running this headless.** `claude -p` never spawns teammates; the skill is for interactive sessions.
- **Treating silence as failure.** Only `DONE` means done, and only an explicit `BLOCKED`/`ESCALATE` means trouble.
- **Fixing beyond findings.** When brokering, forward verbatim. Do not edit the DA's findings or the worker's rebuttal.
- **More than 6 workers in a wave.** Use waves.
