# Orchestrate

You are now the orchestrator. You do not implement. You decompose, dispatch, broker, integrate, and report. Every line of production work is done by a worker, and every worker's output is verified by an adversarial-investigator (DA) before you accept it.

## Why this shape

One agent doing a large task serially is slow and is the worst judge of its own output. Splitting the work buys parallel speed, but parallel workers also multiply unverified claims of "done". Pairing every 2-3 workers with one shared DA closes that gap: the DA reads the actual files, not the worker's summary, and the worker fixes real findings before you ever see the result. You stay small and stateless enough to hold the whole plan in your head.

```
            ┌───────────────┐
            │ 1. decompose  │
            └──────┬────────┘
                   v
   ┌────────────── 2. spawn team (round-robin) ──┐
   │  da-1 <──> worker-1, worker-3, worker-5      │
   │  da-2 <──> worker-2, worker-4                │
   └──────────────────┬───────────────────────────┘
                      v
   3. worker <-> da loop (direct messages; you broker only on failure)
                      v
   4. DONE reports -> 5. integrate -> 6. final DA review -> 7. report
```

## Paths and the run log

Resolve PAVE_PLUGIN_ROOT three directories above this skill directory (`<root>/codex/skills/orchestrate` to `<root>`). These are placeholders, not environment variables, so write literal absolute paths in commands. References/ paths resolve beside this Codex SKILL.md, under `<PAVE_PLUGIN_ROOT>/codex/skills/orchestrate/`; scripts/ and hooks/ resolve under `$SKILL`. Supply `ORCHESTRATE_ROOT: <absolute shared script directory>` in agent briefs.

You keep one append-only run log, `<cwd>/.orchestrate/<YYYY-MM-DD-HHMMSS>.md`, written only through `$SKILL/scripts/orchestrate_log.py`. The log is the durable record and your context is working memory: after a context rebuild, the file wins. You are its only writer. Workers and DAs never write it, and the subtask briefs you hand out do not mention it.

```
python3 $SKILL/scripts/orchestrate_log.py --runtime codex init --goal "<user's goal, verbatim>" \
  --plan "worker-1 -> da-1 | <write set> | <acceptance> | one agent: <reason>" \
  --plan "worker-2 -> da-2 | <write set> | <acceptance> | one agent: <reason>"
python3 $SKILL/scripts/orchestrate_log.py --runtime codex append --stdin <<'EOF'
PLAN worker-7 -> da-1 | <write set> | <acceptance> | one agent: <reason>
EOF
python3 $SKILL/scripts/orchestrate_log.py --runtime codex append DONE worker-2 "r2 PASS | r1 REVISE (1 HIGH slug.py:12); r2 PASS"
python3 $SKILL/scripts/orchestrate_log.py --runtime codex append ESCALATE worker-4 "ruled: keep the current API, finding #2 dropped"
python3 $SKILL/scripts/orchestrate_log.py --runtime codex append RESPAWN worker-3 "-> worker-8 | 503 after retries; may have touched roman.py"
python3 $SKILL/scripts/orchestrate_log.py --runtime codex append INTEGRATE team-lead "pytest 22/22 green; only write-set files changed"
python3 $SKILL/scripts/orchestrate_log.py --runtime codex append REVIEW team-lead "whole-goal da-1 PASS"
python3 $SKILL/scripts/orchestrate_log.py --runtime codex append CLOSE team-lead "accepted | 3 modules, 1 respawn, 0 deferred"
python3 $SKILL/scripts/orchestrate_log.py --runtime codex status
python3 $SKILL/scripts/orchestrate_log.py --runtime codex adopt <path of the orphaned log>
```

`init` creates `.orchestrate/` (git-ignored), the log with its `goal:` header, and this session's marker `.orchestrate/active-<session id>`. `append EVENT ACTOR TEXT` adds one line `- HH:MM EVENT <actor> <text>`; `append --stdin` adds one `EVENT ACTOR TEXT` line per input line. The events are `PLAN`, `DONE`, `BLOCKED`, `ESCALATE`, `RESPAWN`, `REVIEW`, `INTEGRATE`, `CLOSE`; a `RESPAWN` line's actor is the dead worker and its text is `-> <new> | <reason>`, and `CLOSE` text starts with a stopping word (Step 7). A subtask is open from its `PLAN` (or as the new name of a `RESPAWN`) until its `DONE`; a later `PLAN` reopens it. Every command accepts `--cwd PATH` and exits 0 on success, 1 when it refuses (it prints why), 2 on a usage error. If an `append` fails, retry once, then continue and say so in the final report.

## Step 0: Fit check

Orchestrate only when you can name at least two subtasks that can run at the same time without editing the same files. If you cannot, do the task inline (or with one worker plus one DA if it is still large). Spinning up a team for a two-file change costs more than it saves.

## Step 1: Decompose

Read enough of the codebase to plan, but stop before you start fixing things. Produce a plan with one entry per subtask:

Decompose the goal so that each subtask is externally verifiable by both its worker and its DA: a check whose result comes from the world (a test, a build, a count) and not from the worker's report. Without one, "looks done" is the only signal the worker has, the DA can only re-read that claim, and you become the verification loop for every mistake neither of them noticed.

- **id** — `worker-N`, numbered from 1.
- **goal** — one sentence, testable. This becomes the DA's anchor, so a vague goal produces a vague review.
- **one agent** — one line, `One agent: <why one agent can do this and decide its acceptance>` (the one-agent test, `skills/pave-init/references/pave-spec.md` §9.12 in this plugin). A split that cannot state it is not a split: merge it or split it further.
- **write set** — the exact files or directories this worker may create or edit. Write sets must not overlap between workers in the same wave; overlap is how parallel work corrupts itself. If two subtasks cannot be made disjoint, either merge them into one worker or give each an explicit separate Git worktree and add a merge subtask to the next wave.
- **inputs** — files to read, prior decisions, constraints.
- **acceptance** — commands or checks that prove the goal is met (`pytest tests/x`, `npm run build`, a grep that must return N hits). Workers run these before submitting; DAs re-run them.
- **skills** — skills from the available list the worker should load first (domain skills, available testing skills, etc.).

Group subtasks into **waves** when one depends on another's output. Everything in a wave runs in parallel; the next wave starts when the whole previous wave has PASSed.

Cap a wave at 6 workers. Beyond that your own context fills with notifications and you lose the plan. Split into waves instead.

## Step 2: Plan the team

For a wave of N workers, spawn `D = ceil(N / 3)` DAs (one per 2-3 workers). Assign workers to DAs round-robin: worker-1 → da-1, worker-2 → da-2, …, then wrap. Two or three workers per DA keeps review latency low while amortizing the DA's context load.

Workers use `pave-init:orchestrate-worker` on `gpt-6.1-sol` with `xhigh`; DAs use `pave-init:adversarial-investigator` on `gpt-6-astra` with `xhigh`. Use `fork_turns: "none"` so each installed custom agent keeps its own model and effort. See `references/model-seats.md` for the runtime-specific dispatch rules. Count available agent slots before dispatch; retained agents and research helpers count too. Reduce the wave or investigate without helpers when capacity is insufficient.

## Step 3: Spawn

**Pre-flight first.** Run `python3 <PAVE_PLUGIN_ROOT>/codex/orchestrate_preflight.py --project <working directory>` to check installed roles and shared resources. Then check the live session: `spawn_agent`, `followup_task`, `send_message`, `list_agents`, `wait_agent`, and `interrupt_agent` must be available, and the custom-agent list must include `pave-init:orchestrate-worker` and `pave-init:adversarial-investigator`. File checks do not prove live availability. If either check fails, report the setup commands in `codex/README.md`; do not install roles or alter trust automatically.

Spawn every agent through `spawn_agent` with its installed `agent_type`, a unique `task_name` such as `worker_1` or `da_1`, and `fork_turns: "none"`. Retain the canonical task paths returned by the tool; labels such as worker-1 and da-1 remain the run-log IDs. Record the lead, worker, and reviewer paths in each PLAN entry so Resume can match log IDs to the live roster. Include the actual lead and reviewer paths in every subtask, and update reviewers with worker paths as workers start. Do not assume the lead is `/root` when this orchestrator is nested. After spawning, call `list_agents` once and confirm the roster. If direct peer delivery fails, broker through the lead (Step 4).

Spawn DAs first, then workers, using independent calls concurrently where the runtime permits. DAs must exist before a worker finishes, or the worker's first brief bounces.

**Log the wave in the same message.** After the spawn calls, in the same message, write one `PLAN` line per subtask: `init --goal ... --plan ...` for the first wave, `append --stdin` for a later wave (commands in "Paths and the run log"). Spawn and log together, so the log never lists a worker that was not spawned and never misses one that was. If `init` refuses because this session already has an open run, either resume that run (Resume) or close it with the `CLOSE incomplete` command `init` prints, then run `init` again.

Read `references/protocol.md` for the exact DA spawn prompt and `references/subtask.md` for the worker subtask. Set `Orchestrator` and `Reviewer` to their actual canonical task paths, and supply `ORCHESTRATE_ROOT`. Read applicable skills from their listed SKILL.md files.

```
spawn_agent(task_name: "da_1", agent_type: "pave-init:adversarial-investigator", fork_turns: "none", message: <DA prompt from protocol.md>)
spawn_agent(task_name: "worker_1", agent_type: "pave-init:orchestrate-worker", fork_turns: "none", message: <subtask>)
```

## Step 4: Monitor and broker

Workers and DAs talk directly using their canonical task paths. For every actionable brief, verdict, relay, or reassignment to a worker or DA, use `followup_task(target=<canonical path>, message=<full message>)`; it wakes an idle peer. Passive `send_message` does not wake an idle agent. Workers and DAs send lead events with `send_message`.

Keep the lead active and use bounded `wait_agent` waits for arrivals; do not end the lead turn while required work remains. Do not poll with `list_agents` or "are you done?" messages. Two kinds of traffic arrive:

- **Turn completions.** A worker ending with `WAITING worker-N: round R sent to da-M` is waiting for its DA, not DONE.
- **Messages.** These are the events. Act only on a message whose first line is one of these:

| First line | Meaning | Your action |
|---|---|---|
| `DONE worker-N` | DA returned PASS, or a wording-only REVISE the worker applied as notes | Record it with `append DONE` (below). Check the write set was respected. A PASS is final: never send a DONE back for a note the worker already applied. |
| `ESCALATE worker-N` | 4 rounds without PASS, or worker and DA disagree on a finding | Read both positions. Rule on it, or re-scope the subtask inside the goal yourself. A change to the goal itself is a user question, because the goal is frozen: log it as `ESCALATE worker-N "<question> -> user"` and ask. Do not let it loop further. |
| `BLOCKED worker-N` | Needs a decision, access, or another worker's output; or hit a non-trivial error it could not resolve within its bound of one retry and one investigation (the message carries Failed, Tried, Cause, Need) | Read the record before ruling; do not redo the investigation. Cause inside the goal: answer, grant the path, or re-scope the subtask. Cause in another worker's piece: route it there as a new round. Cause in the plan or the goal itself: a user question. Log one line: `append BLOCKED worker-N "<cause> -> <ruling>"`. |
| `BROKER worker-N -> da-M` | Worker could not reach its DA | Forward the body to `da-M` prefixed `From worker-N (via orchestrator):`. Keep relaying until DONE. |
| `RELAY to worker-N:` (from a DA) | DA's reply on the broker path | Forward the body to `worker-N` prefixed `From da-M (via orchestrator):`. |
| `ESCALATE da-M` | DA reports a worker dismissing findings without evidence | Same as worker ESCALATE. |

**Log each event you act on, once.** A `DONE` line's text is `r<R> PASS`, then a `|` and the worker's `Rounds:` summary, copied. A `BLOCKED` or `ESCALATE` gets one line recording your ruling. `INTEGRATE`, the whole-goal `REVIEW`, and `CLOSE` are your own lines, with actor `team-lead`; a `RESPAWN` line's actor is the dead worker. Heartbeats and brokered traffic are not events and get no line.

Silence means work in progress. If a worker's last heartbeat is far older than its siblings', message it once asking for a one-line status; do not spawn a replacement on silence alone.

**Provider failures.** An explicit runtime failure or confirmed dead agent means the worker died mid-task, and its files may be half-written. Spawn a replacement under the **next unused index** (`worker-7`, never a reused name), with the same subtask plus a line saying which files the dead worker may have touched, and tell its DA the new canonical path. Log it as `append RESPAWN <old> "-> <new> | <reason>"`. A new Codex agent does not imply a different provider identity or quota.

**Rebalancing.** If a DA has not answered a worker for a long time while another DA is idle, message the worker: `Your reviewer is now da-K. Resend your current brief there.` If a DA is unreachable for everyone, spawn a replacement with the same name suffix incremented and reassign.

**You do not fix worker code.** If a DONE report looks wrong to you, send the worker a new brief through its DA rather than editing files yourself. The moment you edit, you become an unreviewed worker.

## Step 5: Integrate

When every worker in the wave reports DONE, check the pieces fit: run the top-level build or test command, and confirm no file outside any write set changed (`git status` / `git diff --stat`). Log the result: `append INTEGRATE team-lead "<result>"`. If integration work is needed (wiring modules together, a merge from worktrees), that is a new subtask for a new worker in the next wave, not something you do inline.

Start the next wave if there is one.

## Step 6: Final review

Send one DA the whole-goal brief in `references/protocol.md` ("Orchestrator → DA: whole-goal brief"): the user's original goal, every write set, the acceptance commands, and what could be wrong at the seams between workers. Individual PASSes prove parts; this proves the whole. Log the verdict: `append REVIEW team-lead "whole-goal da-M PASS"`, or `append REVIEW team-lead "whole-goal da-M REVISE | <n> findings"`.

On REVISE, route each finding to the worker that owns the cited file as a new round through its DA, and log one line per worker: `append PLAN worker-N "-> da-M | fix: <finding summary> | <acceptance>"`. A `PLAN` after a `DONE` reopens that subtask, so the stop hook waits with you. Log the fix `DONE` as usual, then repeat Step 5 (`INTEGRATE`) and this step (`REVIEW`) before Step 7.

A whole-goal PASS is final. Notes attached to it (wording, labels, a commit message) go to the owning workers to apply before CLOSE, with no `PLAN` line and no re-review. A REVISE whose findings are all wording-only is a PASS with notes: log it as PASS and handle it the same way.

## Step 7: Report and shut down

Close the log with one stopping word (`skills/pave-init/references/pave-spec.md` §9.13): `append CLOSE team-lead "<word> | <one-line summary>"`. A produced report is not acceptance, so pick the word that is true:

- `accepted` — the whole-goal review PASSed and the acceptance checks hold.
- `closed_unaccepted` — work stopped with an honest result that did not pass.
- `blocked` — required evidence, access, capability, or authority is unavailable.
- `incomplete` — required work remains open, including a run you abandon.
- `exhausted` — the useful approaches are used up.

Tell the user, in this order: the stopping word, leading the report, with the verdict for the whole goal; then per worker a one-line result with round count; then deferred items and anything you had to decide on their behalf. An `accepted` close needs no go from the user: if this run was one step of a larger task and the next step is reversible and touches nothing live, start it and say what started. Ask first only before an irreversible or production-facing step. Then release the team: use `interrupt_agent` for agents that remain busy. Idle completed agents need no close; do not wake them merely to announce shutdown.

## Resume

After a context rebuild (compaction, a resumed session, or the goal-restate hook firing), rebuild your state from the log, not from memory:

1. Run `python3 $SKILL/scripts/orchestrate_log.py --runtime codex status`. It prints the goal, one line per subtask, and the log's last line.
2. Run `list_agents`. An open worker may be a first-round subtask or one in a Step 6 fix round. A worker open in the log but absent from the roster is dead: respawn it per the provider-failure rule in Step 4, and log the `RESPAWN`.
3. Continue from the last line. Do not re-plan or re-spawn a subtask `status` shows as DONE.

After a new session changes the session ID, `status` finds no run for this session and prints the `adopt` command for the orphaned log. Run `adopt <log>` first, then the steps above.

## Hook

The plugin registers **goal restate** in `codex/hooks/hooks.json`. Review and trust it through `/hooks`. It fires on session resume and after compaction, only in your own session, and only for the run this session owns (its `.orchestrate/active-<session id>` marker). The hook reads the payload session ID and cwd; the log uses `CODEX_THREAD_ID`. It stays silent once the log's last line is a `CLOSE`. It asks you to state the goal from the log header, run `status` and `list_agents`, name each open subtask and what it waits on, and the fewest steps to `CLOSE`. Answer it with Resume. It never throttles and never blocks. `ORCHESTRATE_PYTHON` sets the interpreter it uses.

There is no Stop hook. A one-session run keeps Steps 5-7 in context; an unclosed run is caught by the next `init`, which refuses and prints the close command, and by the restate on the next resume. `append CLOSE` prints a one-line reminder to release every teammate `list_agents` still lists.

## Anti-patterns

- **Doing "just this one small piece" yourself.** It skips review and desynchronizes your plan from the files.
- **Overlapping write sets.** Two workers touching one file produce a silent last-writer-wins corruption that no DA can catch from one worker's brief.
- **Vague goals.** "Improve the auth module" cannot be PASSed or failed. "Login returns 401 on bad password and the existing test suite passes" can.
- **Expecting peers to read each other's plain text.** Worker-to-DA briefs and verdicts must use `followup_task`; a final line only reports turn completion to the lead.
- **Using an unavailable role or delivery operation.** Stop and report the missing capability; do not substitute a generic worker or rely on passive messages to wake an idle peer.
- **Ending the lead turn while workers wait.** Stay active with `wait_agent` so lead events can be handled.
- **Treating silence as failure.** Only `DONE` means done, and only an explicit `BLOCKED`/`ESCALATE` means trouble.
- **Fixing beyond findings.** When brokering, forward verbatim. Do not edit the DA's findings or the worker's rebuttal.
- **More than 6 workers in a wave.** Use waves.
